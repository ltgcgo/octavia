💪 Robust compatibility layers for existing SMF and MIDI parsers/converters, powered by the Musical Instructions Compiler Collection from the Octavia project, **licensed under GNU LGPL v3**. The shims do not incorporate any code from the original implementations, only attempting to mimic their shapes and behaviour via experiments.

This module is also released standalone as `@ltgc/midi-parser-ecosystem` on various registries, to allow transitioning off Node-centric ecosystems to web-compliant ESM, as well as for SEO due to poor existing search index ranking on package manager repositories and search engines. This module does **not** incorporate code generated by LLMs.

## Quick start
Are you looking to migrate from older implementations? If yes, [please read the migration notes](#migration-notes).

### `@colxi/midi-parser-js`
_Documentation available: [buffered](https://jsr.io/@ltgc/midi-parser-ecosystem/doc/~/ColxiMIDIParser), [streamed](https://jsr.io/@ltgc/midi-parser-ecosystem/doc/~/ColxiMIDIParserStreamed). Specific migration notes in sections below._
```js
import {ColxiMIDIParser as MidiParser} from "path_to_js_file"; // Buffered variant, speed first
import {ColxiMIDIParserStreamed as MidiParser} from "path_to_js_file"; // Streamed variant, resource first
const midiFile = await MidiParser.parse(input);
```

## Migration notes
While the shims attempt to minimise the required code changes, a scant few are nonetheless needed. Read below for specifics.

### General notes
#### Abbreviations
- **ATD**: Adaptive Text Decoding. Read the "General notes - additions" section and the relevant MICC documentation for details.
- **SPA**: Smart Port Allocation. Read the "General notes - additions" section and the relevant MICC documentation for details.

#### Changes
- Do not use shims marked as "WIP", even ones with documentation. This is due to the relevant documentation always being finished before actual implementation, to ensure the original codebases never leaking into the shims, thus ensuring zero additional restrictions beyond what GNU LGPL v3 already impose. Only use ones marked as "RC", "Ready" or "Finished".
- As the shims reuse the MICC parsing machinery, they also inherit much stricter validation that came with MICC. As such, corrupt files silently accepted by the original implementations may longer be permitted.

#### Additions
- Input type adapters are no longer needed, as all parsers have expanded input types. For a list of supported input types, [read here](https://jsr.io/@ltgc/octavia/doc/micc/~/UnifiedBinaryIntake).
  - For example with Colxi, if you previously handled files via `MidiParser.parse(await blob.arrayBuffer())`, you can now simplify it to `MidiParser.parse(blob)`.
  - Or if you handled dynamic downloads via `MidiParser.parse((await fetch("https://example.com/test.mid")).arrayBuffer())`, you can now simplify it to `MidiParser.parse(await fetch("https://example.com/test.mid"))`.
- Some parser shims, like the Colxi-family shim, have buffered and streamed variants catering different needs. If speed is prioritised over memory constraint, choose the buffered variant, otherwise use the streamed variant. Actual throughput figures are available in the documentation.
  - For Colxi: [buffered](https://jsr.io/@ltgc/midi-parser-ecosystem/doc/~/ColxiMIDIParser), [streamed](https://jsr.io/@ltgc/midi-parser-ecosystem/doc/~/ColxiMIDIParserStreamed).
- Mojibake (garbled text due to text encoding mismatch) handling is now built-in. All shims use the UTF-8 → Latin-9 → Shift JIS decoding ladder by default, however you can swap them out via the `decoders` property.
  - Some MIDI files may use text encoding indicators to request changes mid-parse, like MMA text encoding tags, Soft Karaoke language tags, and XF region/language fields. Check the "**ATD**" (adaptive text decoding) field for the state of current support, which none of the original implementations actually implement.
- If capable of being represented fully within the constraint of the original classes, all shims now gain free SMF extension supports, like Yamaha XF and MUSEQ. This can be disabled by setting the `extended` property on parser shims to `false`, which usually will match the output of the original implementation.
  - If `Uint8Array` passthrough is not desired, the Colxi shim has an additional `MidiParser.customInterpreter = false;` toggle to produce integers instead. This is also noted in its "changes" section.
- Some MIDI files, notably certain type 1 official demo songs from Roland SC-88 and Roland SD-90, lack explicit port assignments. Some vendors like Yamaha use [custom extensions](https://kb.ltgc.cc/octavia/impl/ext.html#port-assign) to assign ports instead of the standardised MMA conventions. SPA is thus designed to deterministically handle all these multi-port files. Check the "**SPA**" (smart port allocation) field for the state of current support, which none of the original implementations actually implement.

### `@colxi/midi-parser-js`
#### Incompatibilities
- If multiple parser instances with different configurations are needed, due to the original implementation giving few to nothing to customise, it's currently **not supported**. We'll add it at a later date due to its ease of implementation via `ColxiMIDIParser*.new()`.
- If you rely on other semantics exposed by the original parser, but not yet implemented by this shim, we'd love to hear from you about how you actually use the original API, so we can attempt a proper safe behaviour emulation.
- CommonJS is **not** supported, only standard ESM. Runtimes like Node.js and Bun may attempt transparent ESM-to-CommonJS adaptation, but supporting `require` explicitly is never going to be intended.

#### Changes
- The parser objects are now named exports instead of default.
  - As an example, if you imported the original parser with `import MidiParser from`, those should be rewritten as `import {ColxiMIDIParser as MidiParser} from` (buffered) or `import {ColxiMIDIParserStreamed as MidiParser} from` (streamed).
- The parsers are now asynchronous via `Promise`s instead of synchronous.
  - If you depend on callbacks, no changes are needed.
  - If you depend on direct returns, prepend `await` to unwrap the value.
    - As an example, if the code is originally `const midi = MidiParser.parse(arrayBuffer);`, it should now be `const midi = await MidiParser.parse(arrayBuffer);`.
- The parser now throws instead of returning `false` on hard parsing failures. If you relied on `false` equality before, now a `try {} catch` block is required, or we'd love to hear from you if you need the `false` test instead of explicit throws.
- Custom interpreters will still function, and few to no changes are needed if the operations are safe, however they will nonetheless affect the performance of the parser like in the original implementation. Avoid them if possible.
  - [Read the documentation](https://jsr.io/@ltgc/midi-parser-ecosystem/doc/~/UnifiedShimColxi.customInterpreter) on the custom interpreter to understand its semantics.
    - They are only called to interpret `F0` (SysEx new), `F7` (SysEx resume) and `FF` (meta) events.
    - For `FF` events, `metaLength` is the actual size of the meta event payload, and `type` is the type of the meta event.
    - For `F0` and `F7` events, `metaLength` is always `false`, and `type` is always `15`.
  - If you only needed them to populate raw bytes from the event, custom interpreters are now made obsolete. You can now remove the custom interpreter, and optionally specify `MidiParser.customInterpreter = true;` to guard against default behaviour changes.
    - If the original number reading behaviour is desired, raw byte passthrough can be disabled via `MidiParser.customInterpreter = false;`.
  - If they are still needed, note that the shimmed interpreters are now strictly constrained to minimise corruption.
    - Provided raw binary views are copies of original data. This prevents custom interpreters from modifying the original data altogether.
    - Access to the underlying data is now clamped to the constraint of the current event, and out-of-bound accesses will error out.
    - If the custom interpreters throw, they no longer take down the whole parser, and are treated as if the interpreter requests default Colxi-compatible handling, turning the data to integers.
